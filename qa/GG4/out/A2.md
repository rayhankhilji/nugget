# GG4 / A2: learning from Accept/Dismiss (BB2) and reset

Scenario: `qa/GG4/scenarios/learning.py` (deterministic, no model, about 30 s). Audit reader:
`qa/GG4/scenarios/a2audit` (`target/debug/gg4-audit`). No IPC method reads the audit log; only
`status.audit_chain_ok` exists, so the check reads the stopped store directly.
Evidence: `qa/GG4/out/a2/summary.json` (every check with its evidence) and
`qa/GG4/out/a2/evidence.json` (per-day rank tables, resets, audit records).

```
cargo build --manifest-path qa/GG4/scenarios/a2audit/Cargo.toml --target-dir target   # once
python3 qa/GG4/scenarios/learning.py --out /tmp/a2            # all scenarios, ~30 s
python3 qa/GG4/scenarios/learning.py --out /tmp/a2m --only minimal   # the 5-second repro of F1/F2
```

**Method: twin homes.** Each scenario runs two homes on the *same* synthetic mail folder: `U` (the
user gives feedback) and `C` (control, no feedback), both started at the same faketime instant. The
difference in rank between U and C, measured in log-odds, is what learning did to that card. This
shows bleed onto cards the user never touched, and after `reset_learning all` U must match C.
"Offered" means open, rank >= `min_score` 0.45 and not hidden. The inbox is also capped at 12 cards,
which is reported separately.

The users simulated (2026-11-09 to 2026-12-15, America/New_York; a new day is a daemon restart at
a later faketime):

- Recruiter Jo (`talentpeak.example`): dismissed `not_relevant` every day. His colleague Sam at the
  same firm and Lee at another firm are never touched.
- Manager Priya (`larkspur.example`, the user's own domain): accepted every day. Coworker Tom is
  never touched. Coworker Kevin is dismissed `not_important` on days 3 and 4.
- `deals.guy@gmail.com`: dismissed `not_important`. Gmail friends Sofia and Ben are never touched.
- Client Dana: one thread dismissed `already_handled`, then a new message arrives in that thread.
- Rita at a vendor: dismissed `wrong_info`. Omar at the same vendor is never touched.
- A benefits thread that turns sensitive: a reply with an SSN and an IBAN, all synthetic.
- Scenario 2: the manager dismissed `not_important` 5 times, then an urgent ask arrives.
- Scenario 3: one fresh home per dismiss reason, measured in a single session.

## FINDINGS

### F1: Every Accept or Dismiss retrains a shared global model that moves *every* card. One dismissal of a recruiter buries your friends and your manager. (High)

- **Repro:** `python3 qa/GG4/scenarios/learning.py --out /tmp/a2m --only minimal`, then look at
  `report.one_dismissal_of_X_moves_untouched_friend_less_than_0.25_logodds` and
  `six_recruiter_dismissals_keep_friend_and_manager_offered` in `/tmp/a2m/summary.json`.
  The scenario uses one fresh home with 6 recruiter mails from jo@talentpeak.example, a dinner
  question from sofia.alvarez@gmail.com and a question from the manager. The user dismisses one Jo
  card.
- **Expected:** Sofia's card does not move, apart from the small documented `kind` effect
  (≤ 0.2 log-odds).
- **Actual:** Sofia's card moves by this much after one piece of feedback on Jo, depending on the
  reason:
  `{"not_relevant": -0.962, "not_important": -1.051, "already_handled": -0.426, "wrong_info": -0.272, "snooze": -0.354}`.
  The card's `learned` explains only `["kind","unanswered_thread","less",0,1,"not_relevant",-0.111]`.
  The rest is invisible: its factors show the model weights changed under it
  (freshness 0.8→0.646, direct 0.6→0.42, question 0.5→0.32).
- **Six dismissals:** both Sofia and the manager drop from 0.599 to **0.0763** (`eligible: false`),
  with `learned` showing only kind −0.429.
- **Over the full week**, Sofia, Ben and Lee, whom the user never touched, fall below the offer
  threshold on every day 1–4. Against the control their change is −2.2 to −2.7 log-odds:
  `"1": {"sofia": -2.31, "ben": -2.305, "lee": -2.305, "tom": -1.808}`.
- **The manager the user accepts every day** ranks *below* the no-feedback control on day 1
  (−0.267 log-odds) and is only +0.19 by day 4: `{"1": -0.267, "2": 0.146, "3": 0.876, "4": 0.186}`.
  This is despite a learned sender lift of +2.39.
- **Already handled breaks too:** Dana's genuinely new message in a thread marked already handled is
  correctly *not hidden*, but it ranks 0.179 against 0.747 in the control, so it is never offered.
  The same happens on day 35 (0.158 against 0.758).
- **Frequency:** 3/3 runs (deterministic).
- **Owner:** `crates/nugget-proactive/src/lib.rs:406`. This line runs
  `state.model.update_weighted(&features, fb, model_weight(fb, reason))` on every accept, dismiss
  and snooze.
  - `score.rs:172-191` is an SGD step with `learning_rate: 0.3` (`score.rs:95`), and the bias is not
    regularised (`score.rs:180`).
  - `already_handled` and `wrong_info` still train it toward "dismissed" (`lib.rs:603` gives
    0.5 and 0.25).
- **Fix direction:**
  - Now that the BB2 per-scope layer exists, stop training the generic weights (bias, freshness,
    direct, question, importance, urgency) from single cards. Learn only `kind_*` weights, or use a
    learning rate of about 0.01 with the bias frozen.
  - Never train on `already_handled`, `wrong_info` or snooze.
  - Whatever global drift remains should be visible in `card.learned` and bounded by `TOTAL_CAP`.
  - Add a bench assertion that one dismissal of sender X moves an unrelated card by less than
    0.1 log-odds.

### F2: Scoped resets ("forget Jo", "forget this firm", "forget this kind") do not restore the cards. Only "all" does. (High)

- **Repro:** run the full scenario and look at `report.scoped_resets_restore_jo_cards_to_no_feedback_rank`,
  plus `scoped_resets_undo_bleed_on_friend` from `--only minimal`.
- **Expected:** after `reset_learning` sender `jo@talentpeak.example`, then domain
  `talentpeak.example`, then Jo's thread, then kind `unanswered_thread`, Jo's new cards rank as if
  the user had never given feedback.
- **Actual:**
  `"jo-35": [0.36845, false, []]` against control `[0.78868, true]`, a gap of **−1.856 log-odds**.
  The card is still not offered, and `learned` is **empty**, so the user sees no reason and has
  nothing left to reset except "all".
- **Minimal repro:** after the sender, domain and kind resets, Sofia is still −1.947 log-odds and
  `"learned": []`.
- Each scoped reset itself behaves as documented. It removes exactly its entry, only the expected
  cards move, and it is audited and announced. The problem is what it leaves behind.
- **Frequency:** 3/3.
- **Owner:** `crates/nugget-proactive/src/lib.rs:543-557`. `ResetScope::One(..) => {}` leaves the
  shared model untouched. A kind reset restores only the `kind_*` weight, not the bias or the
  generic weights that the same feedback moved.
- **Fix direction:** follows from F1. If the shared model keeps learning, keep per-scope deltas
  so that a scoped reset can subtract them.

### F3: The shared-model part of learning never decays. (Medium)

- **Repro:** full run, `report.shared_model_part_decays_too`.
- **Expected:** "decay so old feedback fades" (BB2), for everything feedback did.
- **Actual:** 31 days after the last feedback, the change against the control that `card.learned`
  does not explain is still −2.3 to −2.6 for every sender:
  `{"jo": -2.461, "sam": -2.558, "priya": -2.32, "deals": -2.475, "sofia": -2.54, "tom": -2.526, ...}`.
  It was about −2.3 on day 1. The learned layer itself does decay; Jo's sender counts fall from
  4.886 to 3.416.
- **Frequency:** 3/3.
- **Owner:** `score.rs:172-191`. The model has no time component.
- **Fix:** as F1. If the model stays, decay it toward the prior.

### F4: A manager dismissed as "not important" a few times can never again surface an urgent ask. Months later it is still 0.8 % against 92.6 %. (Medium)

- **Repro:** full run, `report.bounded_urgent_manager_mail_resurfaces_within_95_days`, and
  `evidence.json → bounded.probes`.
  The user, who has written to the manager 10 times, dismisses 5 weekly-status asks from
  priya@larkspur.example as `not_important`. Then a 12-day-old "URGENT: legal needs your sign-off on
  the release today?" arrives at +5, +35, +95 and +185 days.
- **Expected (judgement):** feedback bounds the demotion, so a very high-urgency ask from someone
  with a strong relationship can come back, at least after a few months of decay.
- **Actual (U rank, C rank, change in log-odds):**
  `{"5": [0.0075, 0.9262, -7.415], "35": [0.0075, 0.9262, -7.415], "95": [0.0084, 0.9262, -7.301], "185": [0.025, 0.9262, -6.193]}`.
  The card is never offered.
  - The learned layer stays within `TOTAL_CAP` = 4 (the check passes). The other −3.4 comes from
    the shared model, which F1 shows is not capped.
  - The learned part does not decay between day 5 and day 35. With a decayed penalty mass of about
    15, the capped sum stays saturated for months (60-day half-life).
- **Frequency:** 3/3.
- **Owner:** `feedback.rs:65` (`TOTAL_CAP` applies only to the learned layer), `feedback.rs:55`,
  and `lib.rs:406`.
- **Fix direction:** cap the *total* feedback effect, model included. Saturate the penalty mass, for
  example by capping a scope's `penalty` at about 5, so that decay can bring it back within weeks.
  Consider letting urgency or explicit deadlines keep a minimum rank.

### F5: Dismissing one coworker as "not important" demotes your whole company domain, including the manager you accept daily. (Low)

- **Repro:** full run, `report.noisy_coworker_not_important_does_not_demote_manager_via_domain`.
- **Expected:** the user's own domain (`larkspur.example`, also `[proactive.engine] user_addresses`)
  is shared by unrelated people, so it should not be a learning key, in the same way `gmail.com` is
  correctly excluded.
- **Actual:** the manager was accepted 5 times and kevin@ was dismissed `not_important` twice.
  `learning_domain_larkspur: {"accepted": 4.886, "dismissed": 1.989, "adjustment": -0.126}`.
  - On day 35 the manager's card shows `["domain","larkspur.example","less",3,1,"not_important",-0.118]`.
  - Tom, never touched, carries the same domain effect.
  - Earlier in the week the reverse bleed applies: the manager's accepts lift every colleague by up
    to +0.5.
- **Frequency:** 3/3.
- **Owner:** `feedback.rs:415` (`sender_domain`) excludes only public and hosted domains.
- **Fix:** also exclude the user's own and internal domains (`Corpus::internal_domains`) from the
  domain scope.

### F6: Resetting a key that does not exist reports success, writes an audit record and broadcasts `cards.changed`. (Low)

- **Repro:** full run, `report.bad_reset_nonexistent_key_gives_clear_answer`.
- **Actual:** each of these returns `{"cleared": 0}` with no error, and each sends a
  `cards.changed` notification with reason `reset_learning`:
  - `{"scope":"sender","key":"nobody@nowhere.example"}`
  - `{"scope":"thread","key":"ffffffffffffffff"}`
  - `{"scope":"domain","key":"gmail.com"}`. This key can never exist, because public domains are
    never learned.

  The audit log gains `["user","sender:nobody@nowhere.example",0]`, `["user","thread:ffffffffffffffff",0]`
  and `["user","domain:gmail.com",0]`.
- **Expected:** `NOT_FOUND` (−32001), "nothing learned about sender nobody@…", or at least no audit
  record or notification for a no-op. The UI cannot tell a typo from a successful reset.
- **Frequency:** 3/3.
- **Owner:** `crates/nuggetd/src/features/proactive/convert.rs:102-131` (no existence check) and
  `crates/nuggetd/src/features/proactive.rs:661-676`.
- The real input errors are good: unknown scope, missing key, empty key, unknown kind and no params
  all return −32602 with a clear message, with no audit record and no notification.

### F7: Decay half-life is 60 days, not the 30 days in the brief, and the user guide says nothing about learning or reset. (Low, needs confirmation)

- **Measured half-life:** 60.000 days. Jo's sender count fell from 4.886 to 3.416 over 31 days.
  This matches `feedback.rs:55` (`HALF_LIFE_DAYS: f64 = 60.0`). The QA brief says "30-day
  half-life", so confirm which one is intended.
- **User guide:** `docs/book/src/guide/today.md:38-39` still says "accepting, dismissing and snoozing
  cards adjusts the weights". It does not describe per-sender, domain, kind or thread learning, the
  "why" line, decay, or the reset control that BB2 requires ("Explain and control").

## What works well

- **Learned layer arithmetic is right and explainable.**
  - After 5 daily `not_relevant` dismissals, Jo's sender entry is `dismissed` 4.8865, exactly the
    sum of the 60-day-decayed dismissals.
  - The day-4 card says `["sender","jo@talentpeak.example","less",0,4,"not_relevant",-2.237]`.
  - The manager's card counts exactly 4 accepts. The extra accept and the `done` on day 0 were not
    counted twice, and `model_updates` did not change.
- **Public-domain protection works.** `deals.guy@gmail.com` dismissed `not_important` 5 times
  creates no `gmail.com` entry, and Gmail friends get no sender or domain effect, only `kind`.
  Hosted and brand domains are handled too (`feedback.rs` MAILBOX_BRANDS / HOSTED_SUFFIXES).
- **Scope separation within the learned layer:**
  - Sender −2.237 is stronger than domain −0.892 (Sam at the same firm), and Lee at another firm
    gets none of it.
  - `wrong_info` gives only a mild sender effect (−0.594) and no domain effect. The vendor colleague
    gets nothing from it.
  - `already_handled` gives Dana's sender **no** penalty. Her other thread carries only `kind`.
- **Thread suppression:** `suppresses: true` appears on the thread entry, and a new in-thread
  message is not hidden.
- **Sensitive data stays out of thread labels.** A sensitive card's title never becomes a thread
  label. When a thread turns sensitive, the earlier non-sensitive label ("Open enrollment: dental
  plan choice?") is also forgotten. No SSN or IBAN appears anywhere in `proactive.learning`.
- **Persistence:** stopping and restarting gives an identical `proactive.learning` (same entries and
  counts), and dismissed cards stay dismissed.
- **Resets:**
  - Each scoped reset removes exactly its entry. Only the cards carrying that entry move. Sender
    keys are matched after trimming and lowercasing (`"  JO@TalentPeak.example "` works).
  - `all` makes U identical to the control: ranks within 2e-3, `model_updates` 0, no entries.
  - Every reset broadcasts `cards.changed` with reason `reset_learning`.
  - Every reset is audited with actor `user`, the right target and the `cleared` count, and the
    audit chain verifies.
  - Reset works while `[proactive] enabled = false`: `proactive.learning` answers, the reset clears
    1 entry, is audited and announced, and once re-enabled the card has no sender effect.
- **Actions are untouched by learning.** For cards that were heavily promoted or demoted, action
  kinds, risk classes and the `cards.preview` archive diff (risk `destroy`) are identical to the
  control's.

## Not covered / caveats

- I could not show a card carrying a `hidden` effect. With a files source, a dismissed card is
  terminal and is never regenerated under the same dedup key, so suppression would only show for a
  *different* conversational card in the thread with no newer activity, which this world does not
  produce. `suppresses: true` and the "new message is not hidden" side are verified.
- The judge was off (`judge = "off"`) so that ranks are pure model plus learned layer. With
  `--runtime` the script passes the model arguments through, but rank then mixes in the judge's
  confidence.
- "Offered" is computed as rank ≥ 0.45 and not hidden, because the 12-card inbox cap confounds
  inbox membership. Raw inbox membership is in the evidence (`inbox`).
